## A. 方向与资源

### Q1 【M0 前】Agent 内核：自建 Rust 薄内核，还是以 DeepSeek Harness（DSH）为内核？
（合并：PRD-Q3、架构-Q1、框架选型-Q1/Q2/Q7、SuperAgent-Q1、故事-Q10/Q12）

你的原始诉求 #2 是"基于成熟开源项目二次开发"。调研 04 推荐阶段一用 DSH；架构 03 选了自建。

| 选项 | 利 | 弊 |
|---|---|---|
| A. 自建 Rust 薄内核 + 库级复用（rusqlite、rmcp、agent-client-protocol、iroh、rig-core），M0 设 2 周止损闸门 | 单二进制、体积小、Node 端与协议类型同一份代码、差异化（多机/事件/策略）完全可控；MVP 不写原生编码 loop，工作量可控 | 偏离"二次开发"字面；内核与降级逻辑工作量有被低估风险 |
| B. 以 DSH 为内核（TS sidecar，Bun/Node） | 最快出 Demo；Session 日志/fork/steer/子 Agent 现成；MIT | developer preview，官方声明会破坏性变更；运行时更重；Bun 单文件 sidecar 可行性未验证；差异化要改内核语义，会逐步变成 fork |
| C. 二开 goose（Rust，Apache-2.0） | Rust、成熟、ACP 双向 | 要承接 goose 的整体产品结构与演进；与"事件内核"心智不同 |
| D. 以 pi 自建子 agent 层 | 轻量、注入点清晰 | TS；子 agent 层仍需大量自建 |

**推荐：A，且 M0 两周按闸门评审；失败则切 B 的混合形态（DSH 仅作 Router 内核，经 ACP/MCP 与 Rust Hub 对接）。** 理由：A 把"最大的轮子"（编码 agent）交给外部 Agent，自建的只是薄层；B 的真正代价是内核语义要被你反复改。无论选哪个，DSH 都会作为一个可被驱动的外部 Agent 存在。

## B. 技术与产品形态

### Q7 【M0 前】桌面壳与前端栈：Tauri 2 还是 Electron？是否锁定 React？
（合并：竞品-Q5、技术栈-Q1、PRD-桌面、UI-Q12、架构-Q6）

| 选项 | 利 | 弊 |
|---|---|---|
| A. Tauri 2 + React，WebKit/Chromium 双内核 CI，保留 Electron 回退 | 安装包 ~57 vs ~323 MB 量级差；Rust 同栈；UI 只依赖 WS 协议故换壳便宜 | WebKit 渲染/性能风险（OpenCode 因此迁回 Electron） |
| B. 直接 Electron | 渲染一致、生态成熟 | 安装包 ~200 MB+；与"轻量"卖点冲突 |
| C. Tauri 3 + CEF | 一致性 | 仍是 alpha，包体≈Electron |

**推荐：A，W2 末和 M1 末各做一次"双内核截图回归"评审，超阈值即切 B；React 锁定。** 理由：决策可逆，且 UI 与 daemon 已协议解耦；React 的 Markdown 流式、diff、xterm、React Flow、assistant-ui 生态资产最全（Vue 栈需重估）。

### Q8 【M2 前】手机端与远程访问：PWA + Tailscale，何时上出站中继，是否要原生上架？
（合并：框架-Q3、技术栈-Q2/Q3、故事-Q7、UI-Q5、PRD-中继）

| 选项 | 利 | 弊 |
|---|---|---|
| A. MVP：PWA 经 LAN/用户自带 Tailscale（HTTPS 由 `tailscale serve` 提供）；M4：自建 Cloudflare Worker 出站 E2EE 中继 + Web Push；原生壳后置 | 最快验证"手机审批"价值；E2EE 中继到 M4 再投入 | MVP 阶段非 Tailscale 用户无法出门审批 |
| B. MVP 就做出站中继 | 开箱即用 | 需自有域名/HTTPS、推送与运维，提前 4–6 周的工作量 |
| C. 直接做 Tauri Mobile / 原生 | 体验最好、推送稳 | 成本高，iOS 审核对"远程执行"类应用有不确定性；iroh 移动绑定成熟度未证实 |

**推荐：A。** 理由：手机只做遥控器，Agent 永不在手机上跑。需要你确认**是否已拥有品牌域名**（中继与配对 deep-link 都要 HTTPS 域名）。

### Q9 【M2 前】多机连接：Hub 放哪、是否强依赖自带穿透（iroh）、离线任务如何处理？
（合并：多设备-Q1/Q2/Q5/Q6/Q7/Q8/Q9、SuperAgent-Q13）

| 选项 | 利 | 弊 |
|---|---|---|
| A. MVP：WS + 配对码 + 用户自带 Tailscale/LAN/SSH；Hub 默认内嵌桌面常驻，推荐用户把 Hub 放常开机器；iroh + 自托管 relay 放 v1.x；Node 离线时任务**不排队**，立即返回 `node_offline` 由编排决定；手机不作 Node | 复杂度最低；行为可预期 | 桌面关机即离线；非 Tailscale 用户跨网络配对需自行解决 |
| B. 一开始就上 iroh | 公钥拨号、约 9/10 直连 | 浏览器不可用、移动绑定未证实、需运维 relay |
| C. 允许离线排队并设 TTL | 体验顺滑 | 过期指令误执行风险，需 Mandate 明示允许 |

**推荐：A；排队仅在任务 Mandate 显式允许时启用（TTL 默认 30 分钟，M4 做）。** 理由：iroh 属于"锦上添花的连通性"，不应卡住 MVP。

### Q10 【M1 前】安全默认值：审批档位、信任模式、Node 本机执行、无人值守
（合并：UI-Q10、故事-Q5、PRD-Q8、多设备-Q5、编程Agent-Q6、SuperAgent-Q8）

| 选项 | 利 | 弊 |
|---|---|---|
| A. 默认"均衡"（worktree 内写放行，R2 及以上询问）；引导提供"谨慎"（所有写也问）与"宽松（信任模式）"；Node 本机 `exec` 默认 ask；无人值守/子 Bot 触发的审批**自动拒且不可关闭**；Agent 内部 bypass/yolo MVP 全禁 | 安全与流畅平衡；可作为卖点 | 审批疲劳需靠"Always 规则 + 作用域"缓解 |

**推荐：A，"信任模式"门槛：仅限已配对且用户明确勾选的设备 + 仅限 worktree 内 + 有 turn 快照。** 个人版不做完整 Mandate/Allowlist 编辑器，先用"设备信任 + 三档主动度（Quiet/Balanced/Chatty）"。

### Q19 【M1 前】UI 范式：永续主线还是每 Agent 一个会话？插话键位
（合并：UI-Q3/Q4/Q11、故事-Q9）

| 选项 | 说明 |
|---|---|
| A. 主 Bot 永续主线 + 子 Bot 各自线程 + 侧聊；运行中输入框即插话（`Enter`=steer，`Alt+Enter`=排队，`Ctrl/Cmd+Enter`=打断并发送）；误发率 >5% 则改为可配置默认 | 推荐 |

| C. `Enter`=发给主 Bot，`Ctrl+Enter`=插话 | 防误发，但弱化核心原语 |

**推荐：A；子 Agent 闲聊彩蛋保留但默认关闭；Goals/Library 放 v1.5，Feed/Ideas 不做。**
